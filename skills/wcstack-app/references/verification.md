# Verifying a wcstack page — the lint, the types, the console, tests, SSR

Read this before you declare a page finished. `SKILL.md` §5 holds the gate itself; this file holds how to run each check and how to read what it says.

## 1. The lint (`@wcstack/lint`, bin `wcs-validate`)

```bash
npx @wcstack/lint index.html                 # while authoring: warnings visible
npx @wcstack/lint --errors-only index.html   # the final gate, once every warning is fixed or explained
```

- **Pass every HTML file and every `wcstack.manifest.json` sidecar as separate arguments.** A `<wcs-state src="…">` file (`.json` / `.js` / `.ts`, a volume's too) is resolved relative to the HTML and read automatically — do not pass it. A `src` from `/` (`<wcs-state src="/app.js">` under `<base href="/ja/">`) is read only with `--root=<dir>`, the directory the server serves as `/`; a `src` the lint cannot read leaves that state unchecked and says so once (`wcs/state-src-unread`, info).
- **Each diagnostic names its code (`wcs/<code>`), a `source:line:col` range and the fix.** Fix every error and every actionable warning, then run it again. A warning can be a real defect — `wcs/binding-path-missing` is a column left empty, `wcs/event-token-unbound` a handler that never runs. The rules and what each means: the Diagnostics section of `packages/vscode-wcs/README.md` in the wcstack repo.
- **Severities follow the runtime**: what makes the runtime fail initialization or a binding is an error; what drops data silently is an error too (`wcs/nested-assign`, `wcs/array-mutation`, `wcs/storage-seed-clobber`, `wcs/input-nested-write`).
- **Files it did not check are named after the counts** — `not read:` for a framework's components and script files (`.jsx` / `.tsx` / `.vue` / `.svelte` / `.js` / `.ts`), `nothing to check:` for a page with no `data-wcs`, no `wcs-*` tag and no wcstack script. Exit `0` with those lines is not a verified page; a framework app is outside the gate — verify it in the browser.
- **Flags**: `--errors-only` (alias `--quiet`) hides warning and info lines but changes neither the counts nor the exit code. `--strict` exits `1` on warnings too — the right CI gate once every `<wcs-state src>` resolves and a `stateSchema` exists, since a path typo is otherwise only a warning; it combines with `--errors-only`. Exit `0` = no errors, `1` = errors, `2` = invalid usage or a file-read failure. `--lang=ja` / `--lang=en` force the message language.
- **Keep the lint at the page's version.** An older lint reports newer syntax as an error (`wcs/lint-version-behind` warns when the page pins a newer minor). 3.x pages stay on `@wcstack/lint@3.5` and the 1.21.x VS Code extension.
- An element marked `data-wcs-ignore` and its content are not checked. Under `$behavior: { enableMustache: false }` nothing about `{{ }}` is reported.

### What the analyzer reads, and what it cannot

- **List rows**: the analyzer follows `$listKeys` for list paths, and takes the row shape of a list that starts `[]` from the row literals in the assignments that add or replace rows anywhere in the script (`this.items.concat({ id, kind })`, `.toSpliced(i, n, { … })`, `.with(i, { … })`, `[...this.items, { … }]`, `this.rows = list.map((r) => ({ … }))`). A row passed as a variable (`concat(row)`) is invisible — inline the literal, or declare a `stateSchema`.
- **Data that arrives from outside** (`catalog: null` filled by `<wcs-fetch>` / `<wcs-storage>`) has no literal: declare its shape with JSDoc on the property — `/** @type {{ id: number, name: string }[] | null} */`, or a `@typedef` in the same script named there (a getter takes `@returns` or `@type`; a getter returning `this.catalog ?? []` keeps the shape).
- **A key written as a name** (`export default { lang, t }`, `items: ITEMS`) has the shape of the `const` or relative import it names. A key whose value is computed at run time (`team: init.team`, `errs: emptyErrs()`) leaves the paths under it unchecked, with one `wcs/path-dynamic-unknown` info: write the seed out as literals, or give the key a JSDoc `@type`.
- **A top-level spread in the state** (`export default { ...defaults(), … }`) hides the keys it brings in: without a `stateSchema` no path of that state is checked. Type the spread's expression (derive the type from the table: a JSDoc `@typedef` with a mapped type over `typeof TABLE`, the table marked `/** @type {const} */`, on the function's `@returns`).
- **The script rules** read what each getter, setter and method reads and writes of the state — the paths it reads or writes that the state lacks, a getter that writes, a setter that writes its own path or a path its getter does not read, a token emitted that nothing receives, a two-way binding on a getter without a setter, untracked reads. A relative path in a row accessor (`this[".name"]`) is read as the path under its row; a relative path in a method is not checked (its row is the caller's).
- **The lint does not see** `bootstrapXxx()` options, `#stop` / `stopPropagation()` around delegated handlers, elements your code moves, element writes used to reorder rows, `[data-wcs]` selectors, or SSR post-processing.

## 2. TypeScript

- **`wcs-schema` — check paths against the real types.** When the state is a TypeScript file (`<wcs-state src="./state.ts">`, or a build that emits `state.js` from it): `npx wcs-schema emit src/state.ts` (from `@wcstack/typescript`) writes `wcstack.manifest.json`, which the lint and the VS Code extension discover (the nearest one walking up from the HTML — do not pass it as an argument unless it should replace discovery). With a `stateSchema`, a path the type lacks is `wcs/path-nonexistent` (**error**) and `for:` on a non-array is `wcs/path-type-mismatch`; paths under a `Date` / `Map` / `Record<string, T>` stay silent. Gate CI with `npx wcs-schema check src/state.ts && npx wcs-validate --strict index.html`, and re-run `emit --merge` after changing the type (`--merge` replaces the named state wholesale; keep hand-written `stateSchema`s only for states you do not generate). A `state.js` works too — `wcs-schema` reads its JSDoc types. The regex analyzer cannot read `users: [] as { name: string }[]` without the schema. `emit` records the state file as `stateSource`, and the schema applies only to the pages whose root `<wcs-state src>` is that file: keep one `wcstack.manifest.json` at the root even when another page has an inline state of its own. A schema whose top-level keys differ from the script's is `wcs/drift-state-key` — regenerate it. Annotate getters' return types (`get total(): number {`); the lint reads them, and methods and `$watch` handlers may carry `: void`.
- **`wcs-tsc` — type-check the inline `<script type="module">` inside `<wcs-state>`** (npm + tsc projects): `npx wcs-tsc --noEmit` (optional peers `@volar/typescript@~2.4.0` + `@volar/language-core@~2.4.0`). The language plugin the VS Code extension uses gives `this` its type, wraps a bare `export default {}` in `defineState` and strips `@wcstack/state` imports, so `this.coutn++` fails as `index.html(9,14): error TS2551 … Did you mean 'count'?` — the write typo that would otherwise create a new key. The script is checked as JavaScript, as the browser runs it: type an inline state with JSDoc (`/** @type {Item[]} */ items: []`, `/** @typedef {import("./api").Item} Item */`), and TypeScript syntax (`const n: number`, `as`, `!`, `import type`) is an error — it would throw in the browser. A `$on` handler's parameters are typed (`state`, `event`, the indexes; `this` is an error) and `this.$command` has exactly the names in `$commandTokens`, in a `.ts` state through `defineState` too. The tsconfig must reach the pages (`include` covering them) and target ES2015+; use `strict`. `wcs-tsc` prints `wcs-tsc: warning: …` about what is missing — pages left out of the program included — and `--wcs-defaults` adds it to a temporary config. Other CDN imports are `any` (`--url-imports=error` to forbid). It checks the script side; the lint checks the HTML side — run both.
- **Building a `.ts` state (Vite).** `<wcs-state src="./src/state.ts">` works on the dev server, but `vite build` emits no state file without `wcstack()` from `@wcstack/typescript/vite` in `plugins`: production 404s the state. The plugin also keeps the inline scripts of `<wcs-state>` and `<wcs-guard-handler>` in the page (Vite takes them out). Without a bundler, compile with `tsc` and point `src` at the `.js`.
- **Both need `typescript` 5 or 6** (the peer is `>=5.0 <7`): install `typescript@6` — a bare `typescript` installs 7, which publishes no JavaScript compiler API.

## 3. The console

- **Every error the engine reports goes through `reportError()`**: a `<wcs-state>` that fails to initialize, a binding that fails to apply (with no `$errorCallback`), a getter / filter / handler / lifecycle callback / `$watch` handler that throws. `window.addEventListener("error", …)` receives each (the console shows it as uncaught; Playwright reports a `pageerror`), the original error as the `cause`. A state with `$errorCallback` sends its binding failures to the callback only — call `reportError(error)` inside it if a reporter must see them.
- **Messages carry the lint's code** (`[wcs/<code>]`), many with a number (`#501`). With the `diagnostics` feature (in `@wcstack/state` and `/auto`) they add the sentence, a did-you-mean and the replacement for a removed 3.x name; on `/core` without it they print `[wcs/<code>] #<number> <values>` — look the number up in the wcstack repo's `docs/state-errors.md`. A bracketed code means the lint reproduces the finding with a range: run it and fix every instance, not just the one that threw.
- **The diagnostics feature warns once about** a bound path that does not resolve, a path a getter reads that does not resolve, a write of an undeclared key beside a near one, a command token emitted while nothing subscribes, a delegated handler reading `currentTarget`, a `$on` handler that uses `this`, two root states, a bound element whose definition never comes, `data-wcs` on `<body>`, inserted markup left unbound, an I/O node's failure nothing reads. The check under-approximates on purpose — **no warning proves nothing**; only the lint checks exhaustively.
- **A `<wcs-state>` that fails to initialize** reports once (`#49`, with the element and its source) and rejects `connectedCallbackPromise`. Causes: a throwing or removed `$` declaration, a source that cannot load (`src="*.json"` HTTP error `#13`, `state="<id>"` with no JSON script of that id `#16`), a second root `<wcs-state>` (`#47`), and a page-level markup error (syntax, unknown filter, wildcard rank). `initializePromise` still resolves; `getBindingsReady(root)` rejects only when every `<wcs-state>` on that root failed before building its bindings; `setInitialState()` on a failed element throws (`#14` — replace the element). A `$connectedCallback` that throws after the bindings are built is `#50`: `connectedCallbackPromise` rejects, `getBindingsReady()` resolves.
- **Two messages point at the page, not at wcstack**: `render chain depth limit exceeded (100 drains …)` is a render loop — a row element's output, a `$renderedCallback` or a `$watch` keeps writing a new value into something the same render reads (`updates did not settle after 32 passes`, `#11`, is the same within one update); write only when the value really changes. `The host row of <x-row> was removed.` is a component's method or a kept `this` (a timer, a continuation after `await`) outliving its `for:` row — check the row is still there, and clear timers in `$disconnectedCallback`.
- **Every package's `bootstrapXxx(config)` throws on an option it does not have**; the lint cannot see those calls.

## 4. DevTools

When wiring is silent and the lint is clean, load `@wcstack/devtools/auto` (before state; on a split auto page add `devtools` to `features=`) and open the wiring pane's coverage view: declared against measured — `$watch` paths (fired ×N / never), command / event tokens (emitted ×N / never), bindings (attached / never attached). The closed badge counts the failures the runtime logged; a Wiring row whose path the runtime reported as unresolved carries an `unresolved` badge. Mount private keys appear only in the State pane's **Overlays** section. The overlay's shadow root is open: a test reads it through `document.querySelector("wcs-devtools").shadowRoot`. Its *prerequisite-missing* note on a row watch with no `for` and no `$listKeys` is a 3.x rule — under 4.0 such a watch fires (read it as "not fired yet").

## 5. Headless tests (npm projects)

A wcstack page is plain DOM: it tests under vitest + happy-dom with no browser, no test-only API and no build.

- **`@wcstack/testing`** (peers `@wcstack/state`, `@wcstack/server`): `const app = await mount(html)` registers the elements and waits for every element and binding (a `<wcs-router>`'s first route too — add `bootstrap: [async () => (await import("@wcstack/router")).bootstrapRouter()]`); a state in its own file mounts with `mount(html, { resolveModule })`. Then `app.state().write(s => …)` / `app.state().read(s => …)` (`app.state<typeof appState>()` types `s`), `fire(el, "click")`, `await settle()`, `app.unmount()`. It shims inline-script state loading, `textContent = 0` rendering as `""`, and happy-dom's parser moving a `<template>` out of a table (insert such markup yourself with `@wcstack/server`'s `setInnerHTML`, not `innerHTML`). Example suite: `examples/state-testing-todo/`.
- **Without the package**: setup file `bootstrapState(); URL.createObjectURL = undefined as any;` (routes the inline state through the `data:` loader — without it the state never finishes loading under Node). Test: `document.body.innerHTML = html` → `await stateEl.connectedCallbackPromise` → `await getBindingsReady(document)` → assert → `await stateEl.createStateAsync("writable", async (s) => { s.count = 42; })` (or `button.click()`) → `await new Promise(r => setTimeout(r, 0))` → assert. Write arrays reactively (`s.items = [...s.items, x]`). Bare Node: `installGlobals()` from `@wcstack/server`, then dynamic-import `@wcstack/state` after it. Details: `state-binding.md` §13.
- `renderToString()` from `@wcstack/server` gives a snapshot test.

## 6. Server rendering (`enable-ssr` + `@wcstack/server`'s `renderToString()`)

- Deploy `@wcstack/server` and the client at the same major.minor: the client discards a snapshot of another minor (3.x included) and renders the page itself. `@wcstack/server` depends on the `@wcstack/state` of its own version, so pinning the server pins the engine.
- Keep the HTML comments in the output — text bindings and row / branch markers are comments; a minifier's `removeComments` breaks hydration and lets `{{ }}` in values be read as bindings.
- Keep JSON values in SSR state (`Date` / `Set` / `Map` / class instances come back as strings or plain objects); derive the rest in getters.
- The render waits for a `<wcs-fetch>` whose url a binding set (within `timeoutMs`); a `<wcs-state src>` renders with `renderToString(html, { resolveModule })`; what the reader typed before hydration is kept. Details: `state-binding.md` §11, `router-and-scaffold.md` §5.

## 7. Serving and the browser

- A static single page needs no server (a tiny one if it fetches). An SPA needs the fallback "every extensionless non-API GET returns index.html" (`router-and-scaffold.md` §7).
- After the checks, run the page in a browser. Working references: `examples/` (multi-package demos) and `packages/*/examples/` (single-package demos) in the wcstack repo.
- In VS Code, the WcStack IntelliSense extension shows the lint's diagnostics inline, with hover, go-to-definition (F12 from a path into the state script), find-references and inlay hints. Other editors get `wcs-*` tag / attribute completion from its `wcs.html-data.json` under `html.customData`.
